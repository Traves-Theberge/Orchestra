# Orchestra task-system contract

This reference describes the current repository implementation. The selected CLI's help is the authority for available commands. Planned Orca-style control features are not operational commands yet.

## Identity and ownership

| Concept | Current representation | Interpretation |
| --- | --- | --- |
| Project | Catalog `id`, `root_path`, optional Git remote/hosted configuration and issue source | A registered checkout/context; not a task or provider HOME |
| Task/issue | `tracker.WorkItem`: `id`, `identifier`, `source`, `project_id`, `state`, `url` | Canonical work item across SQLite/memory/GitHub/Linear/Jira; local tasks are not automatically hosted issues |
| Repository issue | Source + owning repository + issue number/URL | A bare number is not globally unique; confirm repository scope |
| Worktree/branch | Optional task branch/base metadata and running-entry worktree path | Execution resource; task creation alone does not prove it exists |
| Runtime | Running/retry observations, session information and counters | Distinct from Kanban state; not a complete durable run/attempt/workspace contract |
| PR | Linked URL and separately fetched head/merge observations | Review/merge attaches to a commit; it does not imply task completion |
| Native agent/skill resource | Harness + effective/project/global scope + exact native resource ID and content hash | Authored provider-native file; not proof of agent execution or effective selection |

The intended product relationship is repository/project → repository issue/task → worktree → run/provider session → PR. Current local/unlinked tasks and incomplete host/tracker routing must be described as such rather than silently converted into that desired relationship.

Task lists use `id` and `identifier`; detail responses expose `issue_id` and `issue_identifier`. SQLite IDs are UUIDs with separate generated human identifiers. GitHub adapters may use the repository issue number as ID. Match both identity fields plus project; do not reinterpret an arbitrary ID as an issue URL. `project show` resolves the project catalog entry, because the legacy HTTP project-detail endpoint returns statistics rather than catalog metadata.

## Kanban and runtime

The local workflow's stage graph is shown below. State labels alone do not authorize transitions: execution requires plan approval, review findings require replanning, and Done requires the reviewed-head completion control.

```text
Backlog → Todo
Todo → In Progress | Backlog
In Progress → Review | Todo | Backlog
Review → Done | Todo | In Progress | Backlog
Done → Todo | Backlog
```

Backlog → Todo requires title, description, project and assigned worker. Title, description, project and assignee are editable only in Backlog. Review → Todo/In Progress requires feedback. Hosted trackers can have different states; use their actual returned state, not this local transition table, to interpret them.

The CLI exposes separate worker-assignment and provider fields. `task list --unassigned` filters blank/null `assignee_id`; `task list --assignee <worker-id>` filters one exact identity. `task assign --project <project-id> --id <task-id> --request-id <uuid> --assignee <worker-id>` conditionally assigns only a currently unassigned Backlog task in the exact local SQLite project. An optional `--provider` changes the harness only when explicitly requested. The operation does not queue or launch work; a task can remain incomplete in Backlog and queue will continue to reject it until all admission metadata is present. Hosted assignment is not implemented: a remote generic read-then-update has no guarded state/assignee precondition, and GitHub `open` is not Orchestra `Backlog`.

Human task list/show/assign and strict `control tasks` output print persisted `pr_url` verbatim, or `PR: none` when absent. Use `--json` on those commands for the versioned machine-readable envelope. A PR URL is only the stored linkage; it does not prove the PR still exists, matches the current checkout, or is merged.

Todo/In Progress admission additionally depends on assignment, blockers and capacity. A refresh/HTTP acceptance response does not prove a provider started. Local Todo runs planning, then stays Todo at `plan_gate.status=awaiting_approval`; repeated refreshes must not replan a ready plan. Only explicit `approve-plan` with the observed exact `plan_hash` permits execution. Task/context edits invalidate that approval. Legacy In Progress without matching approval is held, not retroactively approved. Hosted gate support is unavailable without a durable source-native contract. Runtime IDLE/RUNNING/retry state is separate from the task's Kanban state. Restart and retry counters are not reliable measures of provider turns.

On Windows, the reviewed default Codex planning/review command explicitly selects its `unelevated` native sandbox with `--sandbox read-only` and native `approval_policy=never`. That subprocess policy does not approve an Orchestra plan or PR. Existing Codex execution-policy rules still apply and can permit commands outside the sandbox; inspect actual stage errors and configured rules rather than assuming every command is restricted identically. On the audited host, repository reads succeeded and a disposable write was denied; the task then stopped at `awaiting_approval`. Other host configurations and harnesses require their own verification.

`task replan` requires the exact project/task, observed current state and plan hash, canonical request UUID and nonempty feedback. It refuses active or unsettled runs, preserves code/worktree and feedback context, invalidates approval and returns to Todo. It does not approve execution. CLI/native-tool requests share receipts; the same UUID and same request reconcile one intent, while changed requests require a new identity. Maestro may approve only on explicit human instruction, and cannot infer approval from an agent's completion or a generic state transition.

PR controls use a provider-independent review attempt bound to exact local project/task, canonical linked GitHub PR, repository and fresh full head SHA. `control reviewers` exposes configured stage capability and installation evidence separately from authentication. `request-review` uses an available harness and the supported `provider-default` native profile; Orchestra's PR reviewer is an application role, not a claim of custom agent selection. It records the attempt before asynchronous dispatch. Findings preserve work and return Todo with feedback; a clean result waits for `approve-review` on explicit human instruction. `complete-review` requires the same approved attempt plus freshly fetched same-head merged evidence and does not merge the PR. Generic state PATCH cannot substitute for these controls. Stored review-gate metadata is historical evidence; refresh PR identity before acting. Hosted task gates and non-GitHub immutable PR adapters remain unavailable.

`status.data` exposes `generated_at`, `counts.running`, `counts.retrying`, and `running`/`retrying` arrays. Running entries currently expose `issue_id`, `issue_identifier`, `state`, `session_id`, `session_log_path`, `turn_count`, recent events/messages, timestamps, provider and token counters. Retry entries expose `issue_id`, `issue_identifier`, `state`, `attempt`, `due_at` and `error`. The current state presenter does not expose project/source identity or worktree paths in these arrays. Correlate only when exact task ID plus identifier has one unambiguous match in the selected backend inventory; otherwise report the runtime entry without assigning a project. Absence from these arrays means not observed in that snapshot, not proof of completion or durable cancellation.

Workspace chat has separate persisted conversation/message identities in `internal/workspacechat`. Its HTTP API accepts `workspace_id` for an observed Git worktree and persists that exact workspace ID/canonical cwd on new sessions; every selected-scope operation checks current authorized membership. Omitted workspace selection belongs only to the registered project root, and legacy root chats cannot appear under children. New Codex conversations support persistent native app-server threads, scoped approvals/questions, interrupt and provider-thread resume; legacy conversations and other providers retain explicit transcript replay. A chat in a task-owned checkout remains a separate conversation identity, not that task's orchestrator run. Provider-reported chat usage is separate from imported account-log statistics; do not sum both as independent billable events. The existing CLI `status` snapshot covers task orchestration and does not include workspace-chat turns. Zero running tasks is not proof that no chat agent is active. The CLI still exposes no workspace-chat control commands; do not use a chat conversation ID as a task/run selector.

The top-level orchestrator is a separate durable chat scope `__orchestrator__`, stored with the same SQLite message/event/request and native thread recovery machinery. It runs in the backend-owned `.orchestra/orchestrator` control directory, not a catalog project or provider HOME. Its native Codex thread declares `orchestra_control` dynamic tools; tool requests must match the active provider thread/turn and declared tool. Unsupported harnesses are disabled for that scope rather than advertised as control-capable. Workspace chat does not inherit these cross-project tools.

## Native agent and skill resources

The CLI's `agent`/`skill` commands use the shared project agent-catalog API. The catalog observes provider-native resources and reports scope, content hash, format, selection status and capability reasons. Effective scope is a read-only view of global plus selected project resources; project scope resolves the current registered Git worktree from its exact workspace ID; global scope reads/writes the shared user-level provider resource files. `__orchestrator__` is reserved for global-only resource operations and cannot identify a project checkout.

Resource IDs are provider-native relative IDs. Nested IDs such as `team/planner` remain one exact CLI argument and are encoded as a query value; do not append `.md`, `.toml` or `SKILL.md`. `show` returns the raw file text and SHA-256 content hash. Create/update read content only from the explicitly named `--content-file`. Update/delete require the latest `content_hash` and a canonical UUID request ID. Stale hashes conflict. The backend records an operation receipt before its filesystem effect; inspect `agent receipt` or `skill receipt` after a timeout or unknown response. The CLI never retries an uncertain mutation automatically.

Receipt completion establishes only that the file operation was recorded as completed. Catalog presence, a detected format or a capability flag does not establish that a provider runtime can parse, load, select or enforce an agent. In particular, Codex/Claude definitions can be discovered while primary selection remains configured-but-unapplied; OpenCode selection depends on the observed CLI capability and still has no effective-agent canary. Skills are resources, not primary agents. Keep provider account settings and global provider configuration outside these commands; only named native definitions/skills are in their scope.

The persistent native orchestrator offers the same shared service as `orchestra_resources` with operations `list`, `get`, `create`, `update`, `delete`, and `receipt`. It accepts only `operation`, `project_id`, `workspace_id`, `harness`, `scope`, `kind`, `resource_id`, `request_id`, `expected_hash`, `format`, and `content`. Kinds are `agent_definition`, `skill`, and narrowly allowlisted `orchestra_config`; resource IDs are exact provider-native IDs, never host paths. `list` returns metadata while `get` returns raw content and hash. Effective scope is read-only; project scope requires exact observed `workspace_id`. `__orchestrator__` permits global scope only and represents shared user-level resources. Orchestra config access is limited to its own `workspace.json`, not provider account settings or credentials. The CLI and tool share hash checks, UUID receipts, and the rule that pending/unknown outcomes must be inspected rather than replayed automatically.

`task create`, `task queue` and `control receipt` use that same shared control service. Create authors a Backlog task; queue changes an exact, complete Backlog task to Todo and requests a refresh. Queue does not certify engine admission, worktree creation, agent launch, provider delivery, PR creation or Done. Project source resolution for these controls fails closed; local/no-source projects use SQLite explicitly. Durable `request_id` receipts deduplicate identical completed requests, reject changed arguments, and retain unresolved intent without replay. This request identity is not a durable run or attempt identity.

Queue is currently limited to SQLite's conditional ID/project/Backlog/required-metadata update. Generic hosted tracker read-then-patch does not supply an atomic precondition, so hosted queue is rejected without sending that mutation. Source-scoped hosted create/observation are not a hosted execution or lifecycle certification.

The shared `assign` control operation persists its UUID receipt before attempting the change. Local SQLite assignment uses one conditional update over exact task ID, project ID, Backlog state and blank assignee. Same-UUID/same-arguments re-observation returns the receipt; changed arguments conflict. It leaves provider unchanged unless one was explicit, preserves PR linkage and reports `execution: not_started`. The CLI does not confuse a human/worker assignee with a harness provider. GitHub's additive `/assignees` route can preserve existing remote assignees, but does not make the pre-read atomic and its `open` state is not Backlog; no hosted write is sent from this command.

## Requested configuration

`provider`, `runtime_target`, `requested_model`, nullable `requested_max_turns`, `disabled_tools`, guidance, criteria and attachments describe requested task context. Requested max turns supports 1–100 or unset in storage, but current production runners do not enforce explicit selected budgets and reject them. No production runner currently advertises the explicit model-selection capability used by the new guard. Do not report these requests as effective.

Generic legacy task creation does not author requested model/max-turn fields; a subsequent patch is a separate operation and can leave a partial result. Running-state snapshots preserve admitted requests; waiting retries are not durable yet. Immutable versioned effective configuration, provider-confirmed settings and crash-atomic admission remain open.

## Legacy mutation effects and routing limits

These endpoints are implementation findings, not instructions to call them outside the CLI:

- Explicit task stop cancels sessions and holds the task in Backlog while retaining its plan, feedback, PR, branch and worktree. Local approval is durably invalidated; starting again requires replanning and approval. The CLI still does not expose stop. Task deletion remains a separate destructive operation that can remove the worktree and branch.
- Generic state updates cannot reopen execution-stage tasks through Backlog/Todo or enter Done. Replanning uses the durable feedback control; Done requires approval of the exact reviewer attempt and fresh same-head merged evidence. Same-state metadata updates retain work. Agent finalization and explicit deletion remain separate flows with Git/cleanup effects; explicit stop preserves work. These observations do not certify provider-session interruption or hosted tracker behavior.
- Backend startup observes terminal tasks without deleting their worktrees. A Done state does not authorize cleanup of unpublished or ignored work. Verify provider-session recovery independently; checkout retention alone does not establish it.
- Project-scoped legacy creation now fails before sending when its configured tracker cannot resolve; local projects explicitly create through SQLite. Returned task project/source/ID must be confirmed before a follow-up runtime-target patch, and the patch must return the same identity. `project_tracker_unavailable` means creation was not sent; `creation_unconfirmed` means an effect may have landed and requires inspecting that tracker before repeating. This legacy HTTP path has no durable retry receipt and does not certify hosted create parity. Project-scoped lists can still fall back globally; detail/search/update/delete still use the global tracker. Even a unique catalog match does not establish that a later operation routes to the same source. The read-only CLI validates the selected project and resolves `task show` from the task list instead of the legacy identifier-detail endpoint; it does not certify consistent source routing or expose those mutations.
- Legacy task creation/configuration can fail after creating the item and has no durable receipt. The bounded control create/queue path persists request intent and confirmations, but an interrupted/unconfirmed external effect remains unknown and must be reconciled. Neither path guarantees exactly-once external tracker behavior.
- Interactive Windows PTY support is not established. The Orca-style terminal resource/handle/send/wait API and durable prompt observations are not implemented in Orchestra. Installed Orca's handles address Orca's runtime, not Orchestra's task IDs.
