# Settings and workspace UX reference audit

This read-only audit identifies settings and interface changes that would bring Orchestra closer to the pinned T3 Code and Orca interaction patterns while preserving Kanban. The first priority is making configuration ownership, failed reads and actual runtime support understandable. Appearance changes can improve navigation and readability, but cannot establish provider launch, terminal or orchestration reliability.

No application settings, provider account files or UI implementation were changed during this audit. Source inspection is evidence of implementation patterns only; neither reference application was executed and no Orchestra E2E claim is made here.

## Recommended execution order and deliberate deviations

First fix failed reads and define a capability/configuration ownership contract. Next add scoped defaults and admitted-run inspection, then settings search/navigation and consistent workspace context. Apply appearance refinements after those states are represented honestly. The already implemented local-folder registration error fix is separate from these proposals.

The executable ownership steps are: inventory each read/write endpoint and its file or database owner; expose backend/profile, provider, project/worktree and absolute write destination beside native-file edits; mark global native CLI edits as affecting that provider's account configuration beyond the current Orchestra task; disable writes while the target read is failed or unknown; distinguish retry from create-file actions; and fence delayed reads and saves by the selected scope. Verify these with isolated account/project fixtures and injected failures before connecting real account settings. This is a data-integrity boundary, not a request for another cosmetic warning panel.

Preserve Orchestra's Kanban and Go/SQLite ownership. Adopt the reference interaction principles rather than copying their full provider-instance, multi-environment or receipt architectures into a cosmetic change. WSL, remote placement, native chat and Antigravity controls require independently verified backend support. Proposed acceptance scenarios above have not been executed by this audit; none of these packages is marked complete.
