## Implemented contract

- `WorkItem.ID` remains the Orchestra storage ID, often source-prefixed. `SourceID` is the identifier sent to the provider API (including the numeric GitHub issue number). `SourceProjectID` holds a Linear team key, Jira project key, or configured repository identity. `ProjectID` on results from the selected-project client is the local Orchestra project UUID.
- Linear configuration accepts `extra.team_key` (or legacy `extra.team`) and the old plain team key in `endpoint`. A URL in `endpoint` is treated as a GraphQL URL, not a team key. Read queries stay team-filtered. Create resolves the configured key to exactly one Linear team UUID, sends the UUID to `issueCreate`, and checks that the returned issue belongs to the same key. Reads of prefixed IDs normalize `linear:<uuid>` before GraphQL. Update/delete/comment preflight the issue and reject missing or foreign team identity before sending a mutation.
- Jira configuration requires `extra.default_project`. Server/Data Center also requires `extra.jira_user`; Cloud allows an empty email for an intentionally supplied Bearer credential. Every configured or custom-JQL search is combined with `project = <key>`, and results must include the matching project key. Creates use that configured Jira key and ignore the local Orchestra project UUID as a Jira key. Prefixed IDs normalize `jira:<numeric-id>` before REST calls. Update/delete/comment preflight and reject issues outside the selected project. Jira Cloud ADF descriptions are reduced to text on reads and descriptions/comments are encoded as ADF on writes. Cloud requests use Basic auth when `extra.jira_user` contains the Atlassian account email and the token is an API token. Server/Data Center uses Basic auth with username and token. Atlassian documents email+API-token Basic auth in its [Cloud REST guide](https://developer.atlassian.com/cloud/jira/service-desk/basic-auth-for-rest-apis/).
- Jira Cloud issue reads use enhanced `/rest/api/3/search/jql`, following Atlassian's [current issue-search API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/); Server/Data Center uses `/rest/api/2/search`. Cloud gateway/cloudId OAuth URL routing is unsupported: the adapter derives REST paths from a standard site base URL. No silent fallback to the deprecated Cloud `/search` endpoint is performed.
- Tracker project browse rows expose `id` and native `key` separately (Linear team UUID vs team key; Jira numeric project ID vs project key). The project link API accepts `{ "config_id": "<exact id>" }` and `{ "config_id": "" }` to clear; either operation atomically clears embedded issue-source fields. Unknown config IDs are rejected before project fields change. Saving an embedded issue source atomically clears the linked config. An omitted token is preserved only for an unchanged source type; provider switches clear the old token. Linked routing reloads the exact related tracker config, preserving its `extra`; populated legacy type/endpoint fields must match that linked config. Legacy embedded Jira cannot carry `extra.default_project`; the factory error directs users to configure a linked Jira connection.
- Linear `Fetch` and Jira search still request at most 100 results; pagination was not added. The Settings form exposes Linear Team key and Jira Project key as required connection fields and persists them in tracker config `extra`; it requires Jira username only when the endpoint indicates Server/Data Center.
- The adapter controls do not claim hosted Backlog-to-Todo admission, durable source mutation receipts, or end-to-end tracker reliability. Linear creation can pass state, priority, and assignee values to the provider; those workflows have only fake-HTTP verification and were not validated against a live account.
