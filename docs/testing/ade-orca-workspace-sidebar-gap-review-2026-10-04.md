## Available Orchestra data and missing ownership

- Git registry observation supplies real path/HEAD/branch/locked/prunable rows and configured-root checks. It does not alone prove which agent works in a row.
- `internal/orchestrator/state.go` already stores running `ProjectID`, `IssueID`, `SessionID`, `WorktreePath`, `RequestedModel`, title, start and last-event/message fields. However, `internal/presenter/presenter.go:StatePayload` currently omits project ID, worktree path, model and title from the public state response. The frontend cannot safely reconstruct those missing fields from a branch label.
- `internal/db/projects.go:Session` and `GetSessions` return project, provider, model, branch and timestamps. SQLite stores `issue_id` and status metadata, but this list omits them and has no durable checkout path. An old session on a reused branch is not evidence that it belongs to the present checkout.
- Native chat session API has project ownership and model/status/time data but no worktree target identity. These sessions genuinely belong to the registered project checkout; they are not a replacement for task agents on other worktrees.
- Frontend task list branch names can label linked tasks, but cannot establish current agent/worktree ownership. A task link must remain a task link until exact execution observations establish otherwise.

## Implementable projection and checks

1. Backend observes repository Git worktrees and exact runtime bindings in one project-scoped response. Agent records carry source, stable session/run/task ID, canonical cwd/workspace identity, provider, requested/effective model distinction, lifecycle/freshness state, title/activity and timestamps. Join only matching project and canonical path. Activity without a resolvable cwd stays an explicit project-level unassigned observation.
2. Separate `is_main_worktree` from `is_registered_checkout`; only the registered checkout owns existing project-native sessions. Historical warehouse sessions need durable issue/workspace evidence before appearing inside another workspace card.
3. Store selected project/workspace path identity by backend ownership. Workspace activation changes the scoped surface; selecting an agent opens its exact native conversation or task-run/session observation. Issue inspection remains a small separate linked-task action, not the workspace-row default.
4. Render Orca's repository heading and flat workspace cards, single direct agent rows, multi-agent summaries, accurate provider icons, real activity/model/time fields and per-workspace disclosure. Use unknown/unverifiable states where current evidence is insufficient. Do not invent child-agent lineage or terminal focus bindings.
5. Verify a populated disposable scene with two repositories, main and linked checkouts, multiple real API observations, retained/unknown activity and duplicate branch labels. Assert that an agent never migrates across repository/path ownership, workspace selection differs from task inspection, a single row has no redundant count summary, and stale backend responses cannot change selection.
6. Capture the populated native Electron sidebar against the user's target. Real Git/API fixture observations and provider transcript fixtures must be identified separately; neither proves an authenticated provider turn or all E2E task lifecycle behavior.

Broad renderer changes remain gated on the integrating agent's data/navigation contract; this review does not mark Orca parity complete.

## Implemented correction and creation flow

The gap review above describes the original surface. The replacement now uses 28px project headings with icon/name leading and disclosure/menu/create controls trailing; worktrees are flat selectable cards. Selection stores the backend-owned canonical path plus stable server workspace ID, changes the actual child resource context and does not inspect a task. Task links remain explicit inspection actions. `primary` badges use `is_main_worktree`, not the registered/native-chat checkout flag.

Native agent lists request each exact workspace ID. Their project/ID/canonical cwd must all match before rendering. Runtime agents come from a captured backend-config `/state` observation and join only exact project and canonical cwd. A single actual agent renders directly; only multiple actual agents show a count disclosure. Rows use provider icons, observed title/activity, requested-versus-effective model labels and actual timestamps. A refresh failure drops active-agent rows rather than leaving stale green activity. Legacy warehouse histories without actual cwd are omitted; child lineage, stale-decay parity and direct terminal-pane focusing are not claimed. Runtime clicks select the actual workspace and inspect the stable task observation; they do not pretend to open a native provider conversation. Expanded projects poll every 15 seconds, with cancellation and backend ownership fences. State reads are currently per expanded project, deliberately awaiting later shared polling optimization.

A subsequent explicit user correction removes the project action menu entirely: only a direct Refresh workspaces button remains, so there is no clipped Open project menu. The tree fills its available sidebar height. Per-project + opens Create worktree; per-workspace + opens New agent. Neither opens CreateTaskDialog.

CreateWorktreeDialog additionally inspected pinned Orca `src/renderer/src/components/NewWorkspaceComposerModal.tsx`, `NewWorkspaceComposerCard.tsx`, and `new-workspace/{NewWorkspaceComposerProjectSection,NewWorkspaceComposerNameSection,NewWorkspaceComposerAgentSection,NewWorkspaceComposerFooter}.tsx` at the Orca revision above. Their observed pattern is a quick creation modal with explicit project/host, Smart source/base, independent registered agent selection, Advanced controls, Create more and screen submit shortcut; the modal initializes an empty prompt. Pinned T3 `apps/web/src/components/Sidebar.tsx` and its thread/header/project controls remain relevant for project-scoped creation and exact thread/worktree context, but its thread-first hierarchy is not substituted for Orca workspace cards. The dialog is an original Orchestra adaptation, not copied reference source.

The new dialog creates a durable Git worktree job, optionally links an explicitly selected existing owned task, and optionally creates a native conversation only after the server confirms a checkout and Git membership is re-observed. It never creates a Kanban task, queues work or sends a prompt. Existing-checkout New agent uses the same native harness/model selector without a Git job. GitHub naming accepts only observed issue references from the configured repository; initial lookup is first-page only and unobserved numbers are refused. Branch selections derive a new target branch from an observed base, without unsupported existing-branch reuse. Unsupported Jira/Linear/GitLab references, remote execution and automatic fetch are explicitly unavailable. Run-on reflects the backend checkout path; a Windows-style path alone is not proof that the backend is this desktop host.

Uncertain worktree requests retain their exact UUID and are checked by GET. Unconfirmed native creation is checked by listing its retained UUID, never by submitting another create. Request/project/backend/provider/model/workspace metadata survives a dialog close or reload in localStorage; API tokens and provider credentials are never serialized. Recovered results require the current exact backend/project and actual Git checkout before selection. Polling stops after a finite observation window and leaves a manual status check. Native model preferences are seeded at creation without launching a provider turn. Completed jobs without a current workspace remain unconfirmed.

### Create-worktree dialog styling and native bounds follow-up

The creation dialog now uses Orchestra's rounded, token-based field and section styling, bounded path truncation, responsive width and focus states. Project, base/source branch, registered agent/model and optional task choices use visible custom listbox controls; their menus portal into the Radix `DialogContent`, preserving its modal focus/pointer boundary and avoiding clipping by the form's scroll area. Menus place above low controls when needed and are clamped to the dialog panel. The dialog keeps its natural compact height, while the form scrolls within the available viewport. The modal's `fixed` positioning is preserved; applying `relative` had displaced the fixed dialog and caused the measured viewport overflow. Nullable branch, remote, provider, issue and model catalog arrays normalize to empty arrays. GitHub's null issue-list response and all four source tabs have regression coverage.
