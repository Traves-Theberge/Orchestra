# Codex provider trust-write diagnostic

The signed-in code canary's account-file integrity gate failed: root's before/after check reports changed Codex `config.toml` bytes, while the checked Claude/Gemini files remained unchanged. The code/edit/revision/restart behavior evidence remains separate from that failed isolation gate. This diagnostic performed source/documentation inspection only; it did not launch an account-connected provider, inspect credential contents, restore a backup, or edit global configuration.

## Matching upstream mechanism

Installed CLI reports `0.160.0`. The upstream `rust-v0.160.0` annotated tag resolves to commit `a956835d020762cb2b570053af06f643a11c0ecc` (tag object `79b1b666f2e8551f8abbbca34957227f67f3f553`). This source match identifies version behavior; it is not binary reproducibility or process-writer attestation.

- [thread_processor.rs, lines 1349–1408](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/app-server/src/request_processors/thread_processor.rs#L1349): `thread_start_task` persists trusted project state when the caller supplies `cwd`, the active project has no trust level, configuration is not projectless, and effective permissions either disable/externalize the sandbox or permit writing the working directory. It resolves the repository trust root, falling back to the supplied working directory, calls the trust setter, then reloads configuration. This path does not require a `config/value/write` or `config/batchWrite` request.
- [core config setter, lines 2411–2424](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/core/src/config/mod.rs#L2411): `set_project_trust_level` uses `ConfigEditsBuilder` to patch `CODEX_HOME/config.toml`.
- [thread-start behavioral test, lines 1530–1594](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/app-server/tests/suite/v2/thread_start.rs#L1530): the writable case expects the project trust entry and loaded project configuration. Its Windows branch expects unchanged configuration when effective sandboxing is downgraded to read-only. The relevant condition is effective permission, not platform name or nominal requested sandbox alone.

Local evidence corroborates the writable branch: [captured native chat](evidence/ade-native-chat-2026-10-04/captured-native-chat.json) reports `sandbox_mode: workspaceWrite` and `approval_policy: never`. The external diagnostic `code-service-canary.py` selected process-local `approval_policy=never` and `sandbox_mode=workspace-write` overrides and inherited the caller's provider home. Orchestra supplies the fixture `cwd` when starting a thread. Root observed a trust entry for that fixture path and configuration modification time matching the canary start.

These facts strongly support upstream automatic project-trust persistence as the mutation mechanism. The byte change is proven by the recorded hash check; exclusive attribution to a particular process is not proven because no OS file-writer trace or exact immediate pre-test content snapshot was retained. An older backup's other trust/TUI differences cannot establish which changes this canary caused. No restoration from that backup is justified by this diagnostic.

The automatic trust path is not specific to Windows sandbox provisioning. On Windows it runs only if effective permissions satisfy the same condition. The observed writable sandbox explains why the upstream read-only Windows test's unchanged-file expectation does not apply here. Reference tests establish source intent, not an independently reproduced Orchestra incident.

## Isolated live-canary strategy

Keep automated protocol/tool canaries on fixture or mock inference with fresh private provider home; existing automated isolation remains the default. A signed-in account canary needs a separate, explicit authentication boundary before further execution:

1. Create a private persistent canary root. Set `CODEX_HOME`, `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, XDG paths and temporary directories there; scrub inherited credential/provider-routing overrides. Keep all fixture projects and native rollouts in that root. Write a minimal canary-owned configuration rather than copying the account configuration, instructions, hooks or plugins. Only reviewed nonsecret options should be reproduced.
2. Prefer a fresh user-operated ChatGPT login into that isolated profile. It creates a canary-owned credential store without copying or linking the existing account credential file. It still uses the selected account's quota; authentication and access must be verified independently. No login was started by this diagnostic.
3. Existing-login reuse is not established as a credential-free option. [Matching auth storage source](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/login/src/auth/storage.rs#L154) binds file credentials to `CODEX_HOME/auth.json`; its keyring key hashes the canonical Codex home at lines 237–245. Moving the provider home therefore does not automatically reuse the original keyring account. [Official app-server authentication documentation](https://learn.chatgpt.com/docs/app-server) exposes account/plan metadata through `account/read`, while external-token authentication requires a host-supplied token and refresh lifecycle. Account metadata is not an access-token export API.
4. A future explicitly authorized credential broker could supply a short-lived access token only in memory to experimental external-token authentication, with no logs, argv, auth-file copy, persisted refresh token, or fallback to the account home. This requires secure token acquisition and expiry handling and is not implemented or verified. Copying/symlinking the existing `auth.json` is not isolation: it transfers credential material and can entangle refresh state or writes with the original account.
5. Record exact private-profile paths and process environment ownership, then check account-file hashes before and after the canary. Expected project-trust mutations must land only in the private profile. A changed account hash fails the gate immediately; preserve evidence rather than automatically restoring an assumed backup. Verify code edits, interruption, session continuity and usage separately from this integrity gate.
