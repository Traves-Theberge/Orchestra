# Usage history retention across incompatible updates

The [comprehensive reference receipt](ade-comprehensive-audit-2026-10-04.md) records inspection of pinned T3 SQLite persistence (`737993303d36e10674c54b95e5bd3826682c99c7`) and Orca versioned session parse-cache persistence (`3284b4c70c901402831bb4ccc5576ea083d2e5ae`) before this repair. Neither reference runtime was exercised. T3 uses explicit migrations and durable SQLite; Orca can discard a disposable incompatible parse cache. Orchestra deliberately rejects an incompatible usage file because it also contains history and scan preferences. No reference code was copied.

Previously, malformed JSON and any unsupported schema were treated as a successful empty store. A subsequent enable/disable or refresh could overwrite the original file. The loader now returns an actionable error and preserves the original bytes. Save publishes its cache entry only after a successful atomic rename. The backend can remain running while usage reports the file error; no implicit recovery/reset or migration is claimed.

`go test ./internal/usage -count=1` passed on Windows. New service-level regressions reopen valid history and reject both malformed JSON and schema-99 state across two independent restarts. Rejected enable and refresh calls leave the existing file byte-identical. Full backend container tests also passed with this repair present. This is usage-store retention evidence, not proof of authenticated agent session continuity, multi-process writes, power-loss fsync guarantees or complete application update recovery.
